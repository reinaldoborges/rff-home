# RF-DSF Architecture Baseline

This document records the agreed design baseline for RF-DSF. It guides the implementation repository; it is not a complete API specification.

## Product shape

RF-DSF is a domain-neutral framework for application and platform engineers building stateful, long-running systems. Coding agents are first-class users of its documentation and examples. The framework is language-neutral in concept, with Go as the first implementation language, and may be paired with a portable, self-hosted runtime.

Reliability, security, auditability, operability, resilience, and disaster recovery are design goals, not blanket guarantees. Both the home repository and the Go implementation use Apache License 2.0; distribution plans remain undecided.

## Logical areas

These are conceptual boundaries; the initial repository and package boundaries are described below.

### Framework

- Provide optional, composable domain-modeling patterns for types, invariants, validation, and transitions without requiring a particular DDD layering, ORM, or base class.
- Provide optional persistence ports and patterns for applications. Applications own their domain data and persistence choices; there is no mandatory ORM or universal data model.
- Define deterministic domain state machines using typed states, events, guards, and transitions. Applications define their state machines and domain validators; execution statuses such as running, retrying, and notifying are not domain states. Nested business statecharts are deferred.
- Group security capabilities under Security while keeping Cryptography, Key Management, Authentication, and Authorization distinct. Authentication may consume crypto and key-management ports; applications own end-user accounts, identity sources, and domain authorization policy. Workload identity is separate.
- Define capability boundaries and safe cryptographic integration principles now. Concrete crypto APIs, key-management adapters, production identity providers, MFA, and SPIFFE integrations await validated use cases.

### Infrastructure

- The optional workflow runtime manages durable orchestration records, schedules durable timers, and invokes application-defined activities. It does not own application domain data or require domain state to be event-sourced.
- A state change is one generic transition execution per entity, separate from the domain FSM. The framework defines its versioned record and typed persistence port; the host application configures and injects an adapter. The framework does not own the entity schema or store. The first implementation may provide a SQLite adapter. Acceptance atomically persists the execution snapshot, idempotency mapping, and one-active-execution reservation, and is acknowledged only after that write is durable.
- The experimental Go FSM API is typed over application-owned entity IDs, state IDs, events, and inputs. A versioned machine uses pure, synchronous application selectors over prepared immutable input; initialization has a separate selector and no synthetic event. Selection returns the target, effective execution policy, and notification default.
- The application owns the committed `current` domain state. The transition record snapshots the source (`previous`) and selected target (`next`); this execution does not change current until target-state work succeeds and the host commits it. On completion, live entity state contains only `current`, while history retains transition endpoints and attempt outcomes, not a generic event log. Terminal records and idempotency mappings have no automatic expiry in the first slice.
- Each entity has at most one active transition execution. A different concurrent request receives an explicit busy/conflict result; an idempotency key returns the existing result only when all semantic request fields match. A renewable persisted lease issues a monotonically increasing per-entity fencing generation. The host's authoritative commit boundary rejects stale generations, including when transition metadata and domain state use separate stores.
- The application evaluates selection and event/guard rules once on acceptance. Persist the chosen target, stable machine ID and version, pinned serializable execution policy, idempotency identity, notification choice, and the minimal input needed for retry. Machine versions pin selectors, target-state hooks, and failure classification; applications may register multiple versions concurrently, but duplicate registrations are rejected. The application supplies a separately versioned input codec with stable semantic identity or a durable immutable reference; retries rehydrate under the pinned version. Transition-record schema versions are separate from machine versions; adapter migrations preserve active executions and history, while the host owns domain-schema migrations.
- An unavailable machine, hook, classifier, codec, or incompatible state value blocks only the affected execution without changing its protocol phase or releasing its reservation. Inspection exposes safe compatibility diagnostics; other compatible work continues. Revalidation clears the block when compatibility is restored, without bypassing control gates, retry schedules, or elapsed deadlines. If semantic equality for an idempotent request cannot be verified, return an explicit compatibility error instead of guessing. An unreadable or unmigratable transition-record schema causes adapter initialization to fail without writing to that store.
- The first slice provides a host-authorized and audited per-execution migration operation before the work-success/commit-pending marker. After attempts are drained or fenced, a side-effect-free application migrator converts the persisted representation; the runtime validates destination compatibility and atomically records the new snapshot and migration history. Migration preserves original request identity, execution and operation identities, reservation, attempt history and counts, deadlines, notification choice, and policy meaning; it does not rerun selection. A stable migration-request ID deduplicates retries, and stale reports cannot advance migrated work. Unknown started attempts count under the existing policy; external effects may continue despite fencing. The host coordinates and verifies any domain-state cutover; no atomic cross-store migration is promised. Commit-pending, notification, and abort-recovery phases remain on their original version until settled.
- The target state's handler runs before the new current state is committed. It receives an immutable typed execution context; after work succeeds, persist a success/commit-pending marker and stable operation ID before calling the host. The host commits `next` only after successful work, checking `previous` and the current fencing generation, and writes a durable receipt atomically with domain state. If metadata and domain state share a transaction, commit the domain state, execution outcome, and enabled notification intent atomically. Otherwise, reconcile the same idempotent host operation from its receipt without rerunning successful work; do not promise exactly-once cross-store effects. Initialization (`previous = null`) invokes the initial state's entry hook. Separate transition, initial-entry, retry, and recovery hooks are explicit; unused hooks may be no-ops.
- A host may definitively reject a commit when the expected source or a current domain invariant no longer holds. Under a current fence it atomically records a rejection receipt for the stable operation ID without changing domain state or creating notification intent. Reconciliation checks an existing success or rejection receipt before re-evaluating the operation; transient failures, unknown outcomes, and stale fences are not definitive rejections. A rejected execution enters `CommitRejected`; the rejection itself authorizes automatic abort and recovery, retaining the reservation and safe diagnostics until successful recovery and durable abort. The rejected commit and successful hook are not retried; migration and notification waiver are unavailable. Recovery cannot guarantee that external effects are undone.
- State policy pins `MaxAttempts` (including the first attempt), per-attempt timeout, overall timeout, retry-delay schedule, and versioned failure classification. The attempt budget is shared by started state hooks, including successful retry hooks. An authorized intervention retry or abort starts a new budget and deadline at control acceptance plus the pinned `OverallTimeout`; automatic abort after definitive rejection also starts a fresh recovery cycle. Preserve the original and prior deadlines, total attempt history, and numbering; identical control replay does not renew them. An automatic retry uses the next configured delay, repeating the last delay if the schedule is exhausted; an empty schedule requires intervention. These are distinct from lease expiry, and the framework supplies no retry defaults. Exhausted or policy-rejected pre-commit work or recovery enters `NeedsIntervention`; retry resumes the blocked stage, while explicit abort starts recovery. `Aborted` requires successful recovery, does not commit the target or restore independently changed domain state, and records that external side effects may remain.
- Successful work commits the new domain state before notification. Notification is configurable by transition and may be overridden for an execution; persist that choice at acceptance. When enabled, create a durable notification intent/outbox and consider the protocol complete on durable handoff, not consumer processing. For separate stores, use the stored intent and host commit receipt to idempotently hand off by execution ID after commit; delivery retries independently. If disabled, complete after the domain commit.
- Notification override is tri-state (inherit the selected default, enable, or disable). The typed execution status is `Waiting`, `Running`, `Notifying`, `NotificationRepair`, `NeedsIntervention`, `CommitRejected`, `Aborting`, `Complete`, or `Aborted`; execution failures after acceptance are persisted as safe, serializable failure data rather than returned as acceptance errors.
- If notification handoff fails after the domain state has committed, retain the new current state and require notification repair or an authorized, durably recorded waiver; do not roll back or abort the committed domain transition. Block a different transition until handoff is durable or waived.
- For the task-manager fixture, the persisted Membership/transition record is the durable source of invitation-notification intent. The in-memory pub/sub channel is transient; reconcile delivery from the persisted record after restart. Delivery failure is technical activity status, leaves the membership Invited, and does not stop its expiry deadline.
- Commands start workflows. External events and explicit human decisions may advance them through typed, durable, idempotent Go API inputs; activities perform side effects outside deterministic state-machine logic. The runtime persists and fires timers, with persisted deadlines authoritative over timer delivery time.
- Workers claim leased activities, renew leases while active, and shut down gracefully. Delivery is at least once; handlers and side effects must be idempotent.
- Applications supply typed retry and timeout policies for activities and transitions. The runtime validates, persists, and enforces the effective policy; in-flight work keeps its pinned policy unless explicitly updated. Retry count, per-attempt timeout, transition/workflow deadline, and overall execution deadline are distinct. Workflow cancellation is explicit and compensation is application-defined.
- Persist workflow transition, attempt, and worker history needed for recovery and diagnosis. Applications own business audit records. Do not persist secrets in workflow payloads or logs; retention periods remain deployment-specific.
- Persist and deduplicate workflow starts and external inputs. Reuse of an idempotency key with a different payload is an explicit conflict. Propagate stable activity idempotency keys, but do not promise exactly-once effects across stores or services.
- The first runtime is a documented single-node baseline. The framework may provide SQLite as its first transition-record adapter, which the host application injects. An in-memory queue is a transient wakeup path; polling and reconciliation recover work after notification loss or process restart. Multi-node coordination is a future capability whose design is deferred.
- A single logical coordinator schedules work, manages leases/retries, and observes worker health. Do not assume process-local ownership is a permanent contract.
- The persisted transition execution is authoritative for state-hook work. Each `Enter`, `Transition`, `Retry`, or `Recover` hook is dispatched to a worker within that execution; it does not create a second top-level durable activity record. The hook receives the immutable typed execution context and returns success or an error, which the pinned application classifier maps to safe persisted failure data. In the first slice, there is no general free-standing activity API or arbitrary typed activity result.
- The coordinator reconciles due and recoverable executions from persistence; wakeups are hints, not the source of truth. It owns the per-entity transition lease and protocol progression, dispatches hook work, and invokes the host's idempotent fenced commit after success. Workers claim and renew separate activity leases, execute hooks, and report outcomes; they never commit domain state. Activity lease generations fence claims, renewals, and reports, while the per-entity transition generation fences the host commit. Stale worker reports are rejected. External effects still require idempotency; these leases do not fence external systems.
- A durable notification intent is dispatched as a separate worker activity with stable identity and idempotency. Its delivery retry lifecycle is independent from transition-hook retries, and transition completion waits for durable handoff rather than consumer delivery. The durable intent remains the source of truth for notification recovery.
- A started worker attempt with an unknown outcome consumes an attempt under the pinned transition policy; a claim lost before an attempt starts does not. The pinned classifier handles unknown outcomes. An authorized retry of unknown `Enter` or `Transition` work runs the `Retry` hook before redelivering the original invocation with the same identity and idempotency key. Failed or unknown `Retry` or `Recover` hooks retry directly under the same policy without nesting another `Retry` hook. Graceful shutdown stops new claims, drains active work while renewing leases until the caller's deadline, then cancels work and stops renewal so the coordinator can recover after expiry.
- Workers report heartbeat, ready/draining state, and capacity. The coordinator reports persistence/coordinator health separately from execution capacity; no available workers means degraded execution capacity, not loss of durable acceptance. Lease TTLs and renewals, stale-worker thresholds, and shutdown deadlines are explicit runtime settings, with no universal timing or availability guarantee.
- Include structured logs, health/readiness checks, and basic workflow/worker metrics. Defer distributed tracing and advanced dashboards until justified by deployment needs.
- Keep the runtime embeddable and typed-Go-first. The Go API supports workflow starts, external event/human-decision delivery, execution inspection, and operator-control requests. The first slice has no built-in HTTP server, webhook/event receiver, or external scheduler ingress; applications may add those as adapters later.
- The runtime enforces phase gates on operator controls: retry or pre-commit abort from `NeedsIntervention`, with retry of recovery resuming `Recover` rather than the rejected or abandoned transition, and notification retry or waiver only from `NotificationRepair`. A definitive `CommitRejected` receipt automatically authorizes recovery, not a commit retry. Migration has the separate pre-commit safety gate above. Controls cannot bypass compatibility checks. The host application owns authorization and actor attribution/audit; the framework has no authentication, authorization, or operator-identity model.
- A local development/test CLI may start and signal task-manager fixture workflows, list and inspect executions, and request retry, abort, notification repair, or waiver through the fixture application's authorization policy. Its test-only operator identity is distinct from task-manager users and grants no group permissions. The CLI makes no production operations or identity claims. MCP integration is deferred pending a concrete use case.
- SQLite is the first implemented adapter for transition records, not an exclusive storage commitment. In-memory pub/sub is only a wakeup mechanism. MySQL, PostgreSQL, object storage, caches, secrets stores, cloud connectors, and dedicated brokers are candidates, not commitments.

### Test Suite

The task manager is a small conformance domain, not the product's first industry vertical:

- Users may belong to multiple groups. Membership and permissions are group-scoped; access in one group grants no access to another.
- A group has exactly one owner, who is also a member, and zero or more members. Ownership transfer is explicit. The owner cannot leave or be removed before transfer or group closure.
- The current owner may immediately transfer ownership to another Active member of the same open group, without recipient acceptance. Self-transfer is invalid. The former owner remains an Active ordinary member, both Membership records and task assignments are unchanged, and owner-only permissions move atomically. Transfer is a direct application-owned command, not a long-running FSM transition, and requires no notification.
- The authoritative domain transaction rechecks the open group, current owner and recipient's Active Membership, atomically switches ownership, and persists the actor, former owner, new owner, time, and idempotency outcome in the application-owned business audit/store. It serializes against transfers, removal and closure so their committed results preserve the invariants. An authenticated original actor may replay an identical request by actor-and-group-scoped key even after losing ownership, membership, or group access; replay is read-only and returns the recorded outcome. Changed parameters conflict; invalid or denied requests produce no successful outcome.
- Transfer revokes the former owner's authority for new owner-only requests, not work already validly accepted. Such work may commit only if current domain invariants still hold, including that the new owner cannot be removed and a closed group cannot be changed; a definitive commit rejection follows the runtime protocol above.
- Tasks belong to one group, may be unassigned, and may only be assigned to current group members. Any current member may create, update, assign, complete, or cancel tasks. Tasks move from open to in progress to done, or may be cancelled before completion; invalid transitions are rejected.
- Before removing a member, tasks assigned to that member must be unassigned or reassigned.
- Membership is a lifecycle record with `Invited`, `Active`, `Declined`, `Expired`, `Revoked`, or `Removed` outcomes. An owner may invite a known user; Invited grants no access. Acceptance makes the membership Active; decline, expiry, and revocation of a pending invitation are terminal. An owner may remove an Active member only after their assigned tasks are unassigned or reassigned; removal ends group access atomically and records the owner and time in the application-owned business audit. The Removed Membership and historical task references remain. At most one Invited or Active membership exists per group/user; re-inviting after any terminal outcome creates a new record, while terminal records remain immutable history.
- Expiry begins when the invitation is issued and is determined by its persisted deadline, not timer delivery time; acceptance is valid only before that deadline. Competing terminal decisions serialize on the membership, and the first valid committed transition wins. A repeated decision with the same idempotency key returns its prior outcome; a different decision after a terminal result conflicts.
- Closing a group revokes pending Invited memberships with a group-closed reason, blocks further membership and task changes, and retains records. Active membership records remain historical, but a Closed group grants no access.
- The fixture uses seeded opaque user identities, not a login or account system. It exercises authorization denials as well as allowed actions. Crypto is tested separately rather than added artificially to the task domain.

## First implementation slice

The first Go slice implements a single-node runtime end to end: typed deterministic state machines, an application-injected transition persistence adapter (with SQLite as the first adapter), transient in-memory wakeups with recovery polling, leased worker/activity contracts, and the task-manager fixture with invitation workflows. The [first-slice acceptance gate](https://github.com/reinaldoborges/rff-home/issues/22) passed; its required black-box scenarios and failure criteria are in the [First-slice acceptance matrix](first-slice-acceptance.md).

The first slice excludes multi-node coordination, cloud-specific adapters, production identity-provider integrations, concrete crypto/KMS APIs, MCP, and a production control plane. Framework APIs remain experimental until validated adopters establish a stable release.

## First implementation repository

The first Go slice lives in [`reinaldoborges/rff-go`](https://github.com/reinaldoborges/rff-go), separate from this home repo, with one root Go module, `github.com/reinaldoborges/rff-go`. This is an experimental import path; changing it later requires consumer migration.

- Provide public `fsm` and `runtime` packages. The FSM is usable without the runtime; the runtime uses the FSM and owns its execution and persistence contracts.
- Put provided persistence adapters under `adapters/`. They implement runtime contracts and are selected and injected by the host. Reusable framework and runtime code must not depend on concrete adapters or the task-manager fixture.
- Keep coordinator and worker implementation details internal where they need not be public. Keep the task-manager fixture and its adapter conformance harness internal, with a runnable local/test fixture CLI under `cmd/`. The harness is reusable across adapters included in the first slice, without committing to a public conformance API.
- Do not create packages for deferred capabilities merely to fill out the conceptual architecture. One module can carry adapter dependency metadata even when an application does not import an adapter.
- Split repositories or modules only when demonstrated independent ownership, dependency, or release needs justify it.

## Home repo responsibilities and deferred decisions

This home repo is the source of definitions, architecture decisions, and GitHub implementation-planning issues. The [coding-agent implementation contract](implementation-agent-contract.md) specifies repository guidance, issue handoff, executable examples and contracts, bootstrap, and verification gates. Implementation PRs link to their home-repo issues and relevant decisions; cross-repository links are not assumed to close issues automatically.

Also deferred: the permanent project name; distribution plans; a real first-adopter workflow (choose one before freezing APIs); multi-node coordination design; additional storage, messaging, and identity adapters; concrete crypto/authentication mechanisms; numeric RTO/RPO and availability targets; and stable API compatibility guarantees.
