A live executable is host-composed. The library does not automatically start a permanent runtime or worker pool. The host starts scans and repeatedly schedules claims.

Workers pull hook activities, not whole FSM transitions. Each RunOne claims at most one eligible hook from durable storage, executes it and reports the fenced result; the coordinator progresses the transition and commits through the host.

Acceptance is not completion. Wakeups are hints; polling recovers missed wakeups and work after restart. A reconciliation loop scans immediately but exits on error.

Triggers are separate. Typed input, timers, notification work and Continuations have durable mechanisms, but the host schedules their respective reconciliation or workers. The renewal CLI uses a bounded synchronous drive loop, not an always-on daemon.

Capacity is local to each worker instance. Durable lease claims arbitrate competing workers; this does not establish a global concurrency limit, fairness or multi-node coordinator support.

Problem: Host code must arrange multiple durable scans and worker calls, recover from loop errors, and shut them down safely; the renewal example demonstrates only a bounded subset.

Solution: Explore a reusable, embeddable lifecycle module that composes the enabled progress paths while leaving domain decisions and persistence with the host.

Locality / leverage / tests: Put scheduling, failure visibility and draining in one place; test durable acceptance before startup, lost wakeup, scan failure, restart, Continuation discovery and shutdown through the lifecycle interface.

Deletion test: Without this composition, each always-on host must rebuild and verify the same progress and shutdown rules. Preserve explicit errors rather than silently abandoning or endlessly masking failed scans.

Problem: A worker already claims durably and renews leases, but a single call does not keep it alive or supply a host-wide concurrency policy.

Solution: Explore making repeated, bounded worker execution part of the lifecycle module, while retaining the existing single-claim behavior as an implementation building block.

Locality / leverage / tests: Reuse claim-loop and drain behavior across hosts; test independent competing workers, empty queues, capacity saturation, lease expiry, stale reports and deadline-driven shutdown.

Deletion test: Repeated claiming and drain handling move to every host if removed. This is not a proposal for distributed coordination or a global limit; ADR 0007 keeps coordinator progression separate from worker activity leases.

Problem: Typed input is persisted and pending input can be reconciled, but the host still connects external reception, handler idempotency, authorization and scheduling; different trigger types do not automatically share one lifecycle.

Solution: Explore reusable ingress composition around the existing durable input and transition mechanisms; decide which real host adapters justify an external seam rather than presupposing an HTTP receiver or broker.

Locality / leverage / tests: Concentrate replay and progress behavior while retaining host authorization and domain mapping; test duplicate and changed payloads, crash after acceptance, handler failure and unauthorized requests.

Deletion test: Without shared ingress composition, each receiving host must arrange durable replay and handler deduplication again. Continuation retains its separate origin-revision fence and policy under ADR 0012; this candidate must not flatten those semantics.

Problem: The existing timer worker must be scheduled by the host and its handler must deduplicate repeated delivery; the renewal demonstration does not wire timers.

Solution: Validate a concrete periodic-start use case before extending timer composition with recurring occurrence semantics; retain host ownership of eligibility, domain records and batch progress.

Locality / leverage / tests: If repeated schedules are needed, centralize occurrence identity and replay; test restart before and after a due time, delayed delivery and duplicate occurrence handling.

Deletion test: The proposed module earns depth only if multiple real workflows otherwise recreate schedule and occurrence recovery; a single host can keep this behavior locally. No exactly-once effect or built-in batch scheduler is implied.

Top recommendation

Deepen the runtime lifecycle first: it makes accepted transition work, worker execution and enabled durable triggers progress in an alive host without each application rebuilding the coordination loop. Explore worker and ingress composition within that context, not as independent promises of new transports or distributed scheduling.
