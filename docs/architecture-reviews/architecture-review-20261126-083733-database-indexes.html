Problem. Ordered polling reads and decodes work before eligibility is checked in Go; due and status fields are not SQL predicates. A larger retained work set can increase candidate inspection.

Solution. Explore queryable eligibility metadata and matching adapter indexes inside the durable work module; change the selection queries as well, since extra indexes cannot filter opaque blobs.

Index directions: evaluate timer completion and deadline with an ID tie-breaker; input channel and completion with ID ordering; and hook/notification eligibility and availability alongside claim ordering. Range predicates, lease expiry, and ordering can prevent one index from satisfying every condition; verify each rewritten query on both adapters rather than assuming a composite index will do so.

Locality: eligibility and indexing change together. Leverage: workers rely on durable selection rather than record traversal. Tests: use adapter-valid due, future, completed, leased, and stale-fence records; verify concurrent claims, identical selection semantics, and candidate query plans.

Deletion test: Removing the selection module would spread eligibility, lease, and claim rules into workers; the complexity does not disappear. Preserve atomic claims, fencing, at-least-once delivery, and serialized-record validation.

Evidence: Hook claim · Timer claim · MySQL notification claim · Input discovery.

Problem. Opening an existing schema validates every execution and several other tables without a row limit; retained terminal history increases the work to inspect, even if an index accelerates joins.

Solution. Explore concentrating validation and its performance evidence without weakening fail-closed initialization; startup cost was not measured in this review.

Locality: validation invariants and cost are reviewed together. Leverage: both adapters gain a common evidence standard. Tests: measure increasing history sizes; inject unreadable records and inconsistent joins and verify initialization fails without writes.

Deletion test: Removing validation would not remove the need to detect corrupt persisted executions; that risk would move to later runtime operations. Problem. An index change affects schema creation, compatibility checks, existing stores, and query behavior. MySQL validates required index definitions but does not repair or migrate an existing schema on open.

Solution. Treat index changes as adapter schema evolution with shared verification of fresh stores and representative query plans. The selected scope assumes disposable existing data, so migration is not required.

Locality: index intent and compatibility evidence stay together. Leverage: one review path covers both adapters. Tests: reject missing or malformed required indexes without writes; test long shared-prefix identifiers and candidate plans on both adapters.

Deletion test: Removing the compatibility checks would push index correctness into operational diagnosis. SQLite full-key uniqueness and MySQL non-unique 256-byte BLOB prefix indexes differ: exact identity checks and serialization must remain correct. In an isolated 20,000-row MySQL experiment, converting timer and input IDs to bounded VARBINARY(256) still produced filesort by default; forcing the full index produced ordered index scans. This does not justify forcing an index or truncating IDs: supported ID lengths and semantics must be established first.

Evidence: SQLite indexes · MySQL indexes · MySQL open and version checks · Index validation · Missing-index test.

Deepen durable work selection first

Both adapters scan ordered work before eligibility is known; MySQL also chose filesort in these fixtures. Queryable selection metadata and carefully matched indexes address the observed access-path gap, subject to semantics and plan verification.
