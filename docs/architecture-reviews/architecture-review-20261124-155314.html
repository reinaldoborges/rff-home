Problem
The stated general Pub/Sub intent is broader than the implementation: the only bus is fixture-private and outbound-only, while framework inputs, notifications, and wakeups have separate contracts.

Solution
Keep the bus internal to the fixture and describe the framework as three optional, host-configured paths; defer a general Pub/Sub module until a concrete shared use case exists.

Benefits
  • locality: durable guarantees stay with runtime
  • leverage: hosts opt into only needed paths
  • tests cover replay, ingress, and wakeups separately
Evidence: NotificationBus explicitly calls itself transient fixture storage; SetNotificationSink injects its delivery callback. Drive reconciles the durable outbox before publishing. Tests cover no-subscriber failure, backpressure, and delivery after restart. Separately, lifecycle notification setup is explicit before start, typed inputs are durable, and wakeups are documented as hints only.

ADR fit: consistent with ADR-0001, ADR-0004, ADR-0007, ADR-0012, and the architecture doc: host-owned persistence, durable notification intent, and recoverable transient wakeups remain distinct.

Problem
The desired future coordination spans several distinct guarantees; a single Pub/Sub seam today would be hypothetical and could blur durable inputs, notifications, and transient hints.

Solution
If multiple hosts repeat the same setup, deepen a host-owned composition module around the existing typed paths; require concrete adapters before extracting shared behavior.

Benefits
  • locality: configuration changes stay per host
  • leverage: repeated setup is paid once
  • tests exercise real adapters through one seam
Constraint: one adapter means a hypothetical seam. The current bus is an internal fixture adapter; no production broker or cross-node coordination adapter is present. The architecture doc defers multi-node coordination, so this is not a recommendation to build the module now.
