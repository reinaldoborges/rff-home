Resolved: completeness versus optional detection

The original selection semantics required mandatory supervised detection and unconditional pending-input completeness. The later integrity decision made sweeps optional and disclaimed guaranteed discovery of hidden rows. The user resolved this conflict in the selection clarification: optional detection and the hidden-corruption exception supersede the earlier requirement.

Concrete case: an authoritative pending input belongs to channel A, but its projection says B. SQL filtering for A never selects it, so candidate validation and a lookup of existing findings cannot discover the omission. A completed past sweep is not a current global snapshot, particularly when records change behind its cursor. The same issue can hide eligible claims or disturb first-by-ID selection.

Agreed contract: when projections agree with records, retain complete lists and ordering. Undetected corrupt projections may hide work, change the globally first/earliest selection, or allow an incomplete successful list. Detected mismatches and known potentially matching quarantined inputs still fail visibly. Record/projection updates remain atomic, and exposed candidates remain validated and fenced. Optional sweeps do not certify a current global snapshot or gate ordinary readiness.

Resolved — identity clarification: the identifier research found that timer/input JSON strings do not round-trip invalid UTF-8. The clarified contract explicitly rejects invalid UTF-8 for execution, timer and input IDs, a new restriction for execution IDs; accepted IDs remain byte-exact and case-sensitive, without normalization, including embedded NUL. No migration or automatic deletion is provided; operators may explicitly recreate disposable stores.

Problem. The pinned queries order and decode rows before evaluating much eligibility; SQLite's observed index scans support ordering, not SQL eligibility.

Solution. Concentrate each workload's queryable projection, transactionally maintained serialized record, selection and candidate validation behind the existing adapter seam; do not make a second active-reservation authority.

Locality: projection changes and claim semantics are reviewed together. Leverage: workers retain durable selection without knowing SQL. Tests: adapter-valid early/late/empty candidates, deadline equality, ID ties, started hooks, notification diagnostics and concurrent fenced claims.

Deletion test: removing selection would distribute eligibility, lease and claim rules to callers; complexity survives. Constraint: global ordering and completeness are conditional on projection consistency; hidden corruption may go undetected.

Evidence: Hook claim · Timer claim · Input discovery · ADR 0007.

Problem. Identity, schema, query and index requirements must evolve together across two genuinely different adapters.

Solution. Deepen validation around the selected unchanged-ID contract, workload indexes, and signed seconds/nanoseconds projections; validate every MySQL session's strict mode, not only one pooled connection.

Locality: index intent and compatibility checks stay together. Leverage: callers see stable invalid-UTF-8 and oversized-ID failures before writes. Tests: 256/257-byte values, multibyte and embedded-NUL IDs, invalid UTF-8 rejection, full-value uniqueness, channel-prefix collisions, timestamp extremes, invalid schemas and non-strict connections.

Deletion test: remove these checks and silent truncation or invalid schema assumptions move to every writer. The 256-byte restriction is new caller-visible behavior, including shared-runtime users of custom adapters. Existing stores are disposable for this effort; no migration or automatic deletion is promised.

Evidence: SQLite schema · MySQL schema · Index decision · ADR 0009.

Problem. A finding on shared execution or reservation data affects multiple operations; a stale observation or unavailable finding lookup cannot safely be treated as no finding.

Solution. Concentrate durable findings, non-reused locators and dependency-aware quarantine checks with the existing claim and mutation transaction; use optional checkpointed sweeps only as described by the integrity decision.

Locality: quarantine propagation and fences are reviewed together. Leverage: unaffected work can proceed after its own validation. Tests: stale revisions, unknown edges, unavailable lookup, unknown input channel, in-flight reports and independent work.

Deletion test: removing a shared finding module pushes quarantine checks into every dependent path. Limitation: quarantine applies to known findings; optional checks do not guarantee discovery of rows hidden by a corrupt projection.

Evidence: Integrity supervision decision · Quarantine dependency decision · ADR 0004 · ADR 0007.

Problem. Normal fail-closed initialization can prevent workers from starting, yet a projection repair cannot safely fabricate authoritative transition history.

Solution. Separate worker-free authorized inspection and repair from normal initialization, retaining schema, transaction, audit, revision and fence checks; host-controlled trusted restoration handles unreadable authority.

Locality: repair and audit occur together. Leverage: one guarded maintenance path can serve both offline recovery and coexistence with unrelated work. Tests: unavailable audit/finding storage, changed revision, missing record, restore/recheck, and no partial repair on conflict.

Deletion test: without guarded maintenance, recovery either remains unavailable or moves into ad hoc writes. Worst case: a started hook may already have caused an external effect when its transition execution becomes unreadable. Do not automatically retry, abort or delete; preserve evidence, quarantine the trusted scope, seek host-controlled restoration, and keep it quarantined if the outcome cannot be established.

Evidence: Maintenance decision · Worst-case recovery scenario · ADR 0009 · ADR 0013.
