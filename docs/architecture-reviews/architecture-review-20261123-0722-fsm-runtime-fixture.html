Failure mode · an unnecessary coupling

Observed · independent FSM, host-owned composition

flowchart LR App[Application] --> FSM[FSM] Example[Standalone example] --> FSM FTests[FSM tests] --> FSM Runtime[Runtime] --> FSM Fixture[Task-manager fixture] --> Runtime Fixture --> FSM Runtime --> Port[Persistence port] Port --> Adapter[SQLite adapter] ITests[Fixture integration tests] --> Fixture

Finding

There is no package-level FSM/runtime coupling: fsm uses standard-library code and internal/nilcheck; its selectors and handlers are tested directly, and the standalone example uses no runtime or persistence. Fixture tests cross into runtime intentionally.

Recommendation

Make no package split or new seam. Keep FSM selection tests in fsm and fixture tests for runtime, persistence, and task-manager integration.

Wins

  • locality: selector failures stay in FSM tests
  • leverage: applications use FSM without runtime
  • integration tests retain fixture coverage
  • no duplicate seam or adapter

Fits ADR-0001 and ADR-0006: deterministic state-machine selection remains separate from persisted transition execution. ADR-0004 keeps persistence host-supplied.

Top recommendation

Keep the current FSM/runtime split

Direct FSM tests and the runtime-independent example already demonstrate the intended seam. The fixture composes the FSM with runtime and persistence as a host integration; no structural refactor is justified.
