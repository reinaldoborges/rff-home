Problem: Hook results report success or failure, not a next event; the entity remains reserved during the hook, and an in-memory follow-up after commit can be lost on crash.

Solution: Explore a durable continuation module at the host/runtime seam, without changing application ownership of the next-state decision. A host-owned transactional outbox plus reconciliation is a possible adapter, not a currently guaranteed facility.

Locality / leverage / tests: Concentrate replay, readiness and failure handling once; test crashes before and after commit, duplicate delivery, ErrBusy, rejected commits, and human decisions after a long wait through the module interface.

Deletion test: Removing continuation handling does not remove its complexity; every automatically advancing host must rebuild it. Notification intent is optional, and delivery is independent, so it is not itself a general automatic-transition guarantee.

Hook result · commit receipt and fence · same-file commit and release · ADR 0001 · ADR 0002.

External adapters + fenced domain commit

Problem: Retries and recovery are per transition hook, not per downstream call; a timed-out hook can continue and recovery cannot guarantee reversal of an external effect.

Solution: Explore concentrating host-owned effect identities, receipts and reconciliation behind a deep module; split work across meaningful states where the domain permits it. Do not assume one state automatically provides exactly-once calls.

Locality / leverage / tests: One place to handle duplicate and unknown outcomes; test a downstream success followed by process loss, retry, late completion and definitive commit rejection against the same seam.

Deletion test: Without this module, receipt and idempotency rules recur in each hook. Use an adapter seam where actual downstream implementations vary; avoid inventing one for a single hypothetical dependency.

Stable attempt metadata · hook progression · timeout caveat · ADR 0002 · ADR 0010 · ADR 0011.

Problem: Per-entity acceptance and hook retry do not define batch enumeration, atomic fan-out, aggregation or per-record checkpoints.

Solution: Explore a host batch module once a concrete renewal or payment workflow establishes whether batch-wide or per-record identity is meaningful; retain the existing per-entity runtime protocol.

Locality / leverage / tests: Reuse progress and reconciliation across recurring runs; test duplicate schedule, crash mid-fan-out, one record failure, rerun and concurrent writes. Validate scale separately: reconciliation scans active executions and the MySQL adapter serializes transactions.

Deletion test: If more than one recurring workflow needs durable fan-out, deleting this module would spread enumeration, retry and completion rules across hosts. With only one workflow, keep it application-local until reuse is real.

Top recommendation

Transition continuation first: it connects successful state work to the next requested transition without losing progress between commit and the next request, and is shared by automatic multi-step and batch workflows.
